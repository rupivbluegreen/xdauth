# RFC 10027 compliance

[RFC 10027](https://datatracker.ietf.org/doc/rfc10027/) (BCP 247, *Best Current Practice for Security of Cross-Device Flows*, August 2026) is the finalized version of the IETF draft the README and threat model already cite as this project's design basis. It names two attack classes — **CDCP** (Cross-Device Consent Phishing, exploiting the unauthenticated channel between the device starting the flow and the device approving it) and **CDSP** (Cross-Device Session Phishing, tricking a user into forwarding a session-transfer code) — and lists 17 mitigations in §6.1.2–§6.1.17 (§6.1.18 is a summary table, not a mitigation), plus protocol selection guidance in §6.2. This page maps every mitigation against what `xdauth` actually does.

This revision re-verifies every row against the published RFC text (the prior revision was built from a summarized read and said so). Two rows changed as a result of that re-read, independent of any code change: see "Corrections from re-verification" below.

## §6.2 protocol selection: where xdauth sits

RFC 10027 recommends, in order: FIDO2/WebAuthn (proximity-based, via BLE hybrid transport, §6.2.3) as the preferred approach "when feasible"; the Device Authorization Grant ([RFC 8628](https://www.rfc-editor.org/rfc/rfc8628), §6.2.1) and CIBA (§6.2.2) for constrained-input devices, both flagged as needing the §6.1 mitigations layered on top since neither is proximity-based on its own.

`xdauth` targets exactly the case where FIDO2's proximity model doesn't apply: a headless SSH host or CI runner and the user's phone/laptop are typically not in the same room, let alone BLE range — that's the whole point of "air-gapped." So it takes the RFC's second-choice path (Device Authorization Grant's shape, specifically the User-Transferred Session Data Pattern of §3.1.1) and applies the §6.1 mitigation set itself, rather than relying on the IdP or leaving it to the implementer as RFC 8628 does.

**Where proximity is available, `oidc.Config.RequiredAMR` (`XDAUTH_REQUIRE_AMR`) lets the operator require it without xdauth building a second protocol.** If set (e.g. `hwk,swk` for a hardware- or software-secured key per RFC 8176), the broker rejects any ID token whose `amr` claim doesn't include one of the listed values — so only logins where the IdP itself asserts the user authenticated with a FIDO2/WebAuthn-class credential are accepted. This is a deliberately delegated design: xdauth never becomes a WebAuthn relying party (no credential storage, no new attack surface), and proximity/phishing-resistance verification stays exactly where the RFC says primary authentication belongs — at the IdP (see "What is explicitly not this project's job" in `docs/threat-model.md`). A directly-integrated WebAuthn RP mode remains a possible future addition if a deployment needs xdauth to work with an IdP that can't assert `amr` this way, but delegation is the right default: it is strictly less code and less risk for the same proximity guarantee.

## Corrections from re-verification

- **Mitigation 16 (Request Initiation Verification, §6.1.16)** is specifically: send an OTP/PIN to the *Authorization Device* and have the user enter it on the *Consumption Device*. That is the reverse of xdauth's shape (code shown on the Consumption Device/terminal, entered on the Authorization Device/browser) — the prior revision of this doc conflated mitigation 16 with the base user-code mechanism (which is actually mitigations 2–4). Corrected below to **not implemented** as literally specified; the base pattern's own binding is what checks 2–4 and the WS1 fix (below) actually secure.
- **Mitigation 17 (Request Binding with Out-of-Band Data, §6.1.17)** describes a *human-recallable* datum (a serial number, PIN, or similar) folded into the QR/code and verified by the person. PKCE's `code_verifier` is a machine-only secret never shown to a human, which is the *sender-constrained token* pattern (mitigation 12) — already counted there. Counting it again under 17 double-counted the same mechanism. Corrected to **N/A** for this specific human-verifiable pattern.

## A fixed implementation gap: approval was not bound to the authenticated browser

Independent of the RFC mapping, an implementation bug meant `GET /auth/verify/{id}` served the approval page and a valid session cookie to **any** browser once a session reached `awaiting_approval` — not only the browser that had just completed the IdP login. Since the client that calls `/auth/start` already holds the `user_code`, an attacker who phished a victim into merely *authenticating* (no code needed) could then open the same link in their own browser and submit the code themselves. This collapsed check 2 (number matching) to no protection at all for this attack shape. Fixed by binding a per-browser secret at identity-bind time and requiring it at approve (`internal/broker/handlers.go`, `TestIntegration_UnauthenticatedBrowserCannotApprove`). See `docs/threat-model.md`.

## §6.1 mitigations, one by one

| # | Mitigation | Status | Where |
|---|---|---|---|
| 1 | Establish proximity | **Structural gap for the core case; optional via delegation** | Not implemented as a broker-side check; not a coherent concept for the air-gapped/headless target case (see below). Where proximity is available, `XDAUTH_REQUIRE_AMR` requires the IdP to assert a FIDO2/WebAuthn-class credential (§6.2.3) before the broker accepts the login — proximity is verified by the IdP, not xdauth. |
| 2 | Short-lived / time-bound codes | **Yes** | `SessionTTL`, default 5 minutes (`broker.go` `applyDefaults`). |
| 3 | One-time / limited-use codes | **Yes** | `poll()` consumes an approved session exactly once (`TestPoll_ApprovedIsSingleUse`); `approve()` is only valid from `AwaitingApproval`. |
| 4 | Unique codes | **Yes** | Session id and user code are freshly random per `newSession` call, never derived from client input; a replayed poll of a consumed session is now also flagged as a `consumed_replay` security event (`internal/broker/detect.go`). |
| 5 | Content filtering | **N/A** | Nothing here forwards the code/URL through a message channel `xdauth` controls — the user types the `verification_uri`/code themselves from the terminal. Relevant only if a caller chooses to email or SMS it, which is outside this project. |
| 6 | Detect and remediate | **Partial** | Wrong codes, identity mismatches, repeated `/auth/start` per hint, and consumed-session replay are counted and logged as security events, with an optional webhook on a threshold trip (`internal/broker/detect.go`). No automatic revocation or token-introspection endpoint yet — mitigated in part by mitigation 10 now being implemented (short artifact TTL). |
| 7 | Trusted devices | **Optional, off by default** | `ClientAuthenticator` (`StaticTokenClientAuth`, `MTLSClientAuth`) gates `/auth/start` when configured (`XDAUTH_CLIENT_AUTH_TOKENS`); unset, any client can call it, as in the demo. |
| 8 | Trusted networks | **Optional, off by default** | `XDAUTH_ALLOWED_CLIENT_CIDRS` restricts `/auth/start` to specific networks when set. Independently, `resolveClientIP` now only trusts `X-Forwarded-For` from configured `XDAUTH_TRUSTED_PROXIES`, which also fixes per-IP rate limiting collapsing behind an untrusted or unconfigured proxy. |
| 9 | Limited scopes | **N/A to this layer** | The broker hands back an identity artifact, not an OAuth-scoped access token; scope limiting is the consuming application's job once it mints its own session/JWT. |
| 10 | Short-lived tokens | **Yes** | The artifact itself now carries `ExpiresAt` (default 120s, `XDAUTH_ARTIFACT_TTL_SECONDS`), independent of the session TTL (mitigation 2). |
| 11 | Rate limits | **Yes** | Per-IP and per-`login_hint` token-bucket limiters on `/auth/start` (`ipLimiter`/`hintLimiter`, default 1 per 5s, burst 5), now keyed on the trusted-proxy-aware client IP. |
| 12 | Sender-constrained tokens | **Yes** | PKCE (`code_verifier`/`code_challenge`) binds the approved result to the process that started it, enforced in `poll()`. |
| 13 | User education | **Out of scope for code**, addressed in docs | README "Provider notes" and this doc exist partly for this reason. |
| 14 | User experience: clear context | **Yes** | The approval page always shows client host, IP, kind, and start time before a decision is possible (`TestApproveTemplate_AlwaysShowsRequesterContext`); when client authentication (mitigation 7) is enabled, a verified client id is shown distinctly from the self-reported host (`TestApproveTemplate_ShowsVerifiedClientWhenPresent`). |
| 15 | Authenticate then initiate | **Optional, off by default** | Same `ClientAuthenticator` as mitigation 7 requires the caller to already hold a credential before a session is created. Off by default, compensated for (not satisfied) by identity match at the end. |
| 16 | Request initiation verification | **Not implemented** | The RFC's specific OTP-to-Authorization-Device mechanism is not built. The base pattern's own binding — approver must be the browser that authenticated — was a confirmed gap until the WS1 fix above; it is now correct, but that is a correctness fix to the base pattern, not an instance of this mitigation. |
| 17 | Request binding with out-of-band data | **N/A** | This specific human-recallable-datum pattern isn't implemented; the machine-level equivalent (PKCE) is mitigation 12, already counted there. |

## The one real structural gap: proximity for the air-gapped case

Mitigation 1 (and the RFC's overall preference for FIDO2/WebAuthn) assumes the two devices *can* be near each other and that proximity is a meaningful signal. For `xdauth`'s target scenario — a cloud SSH host, CI runner, or air-gapped VM being approved from a phone that could be anywhere — proximity isn't just unimplemented, it's usually not a coherent concept to enforce, and no configuration flag changes that. `XDAUTH_REQUIRE_AMR` helps only in deployments where proximity *is* meaningful and the IdP can assert it; it does not make the air-gapped case proximity-checked, and isn't meant to.

## Net assessment

Of the 17 mitigations: **7 fully implemented** (2, 3, 4, 10, 11, 12, 14), **4 implemented but optional/off by default** (1 via `XDAUTH_REQUIRE_AMR` delegation, 7, 8, 15 — enabling them meaningfully strengthens the posture beyond the demo default), **1 partial** (6), **4 not applicable to a broker at this layer** (5, 9, 13, 17), and **1 not-implemented-as-specified** (16, the RFC's literal OTP-to-Authorization-Device mechanism). This is a more conservative count than the prior revision (which had double-counted PKCE under 12 and 17, mismapped 16, and treated 1 as purely structural with no available mitigation), and it's a stronger actual posture: mitigation 10 moved from partial to done, mitigation 6 moved from bare rate-limiting to real anomaly detection, and 1/7/8/15 moved from not-implemented to available-and-tested. The four checks in `docs/threat-model.md` map onto the RFC's own highest-leverage mitigations for this pattern (unique/one-time codes, sender-constrained binding, clear UX) — this project is an implementation of what BCP 247 recommends for this constrained-input, no-proximity case, not a novel approach.
